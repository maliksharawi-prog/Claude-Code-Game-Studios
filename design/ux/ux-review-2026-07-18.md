## Open-Question Dispositions

The governing task named four flagged Open Questions to assess for MVP-blocking status. Each
is addressed below, plus one additional item this review is escalating on its own initiative.

### 1. 320px-width legibility (`hud.md` §7, cross-referenced by `main-menu.md` and `pause-menu.md`)

**Not MVP-blocking.** `.claude/docs/technical-preferences.md` names Mobile (iOS/Android) as the
primary target and Web as secondary ("Unity WebGL optional later"). No modern mobile device is
expected to report a logical viewport width anywhere near 320px in 2026 — the scenario `hud.md`
itself identifies as the actual risk is a narrowed **desktop browser window** on the Web
secondary build, not a phone. `hud.md` already gives this a concrete, implementable mitigation
(a `MIN_SUPPORTED_LOGICAL_WIDTH_PX` floor with a "widen your window" notice below it) and a
correctly-scoped deadline ("Before Web export QA pass"). **Ride as an open question** — resolve
it as part of Web export QA, not before mobile-first MVP HUD/menu implementation.

### 2. World Map header logo/title treatment (`main-menu.md` §15)

**Not hard-blocking for a first implementable pass, but the item most worth resolving soonest
of the four.** The document already proposes a concrete placeholder (a lockup in the header's
left slot) and explicitly separates the two sub-questions that matter for implementation
sequencing: (a) *whether* a logo/wordmark exists at all, and (b) the header zone's exact pixel
height, which the document already recommends deriving from `hud.md`'s
`HUD_SAFE_AREA_TOP_INSET_PX` convention independent of what fills the slot. A `ui-programmer`
can build the header zone today with a placeholder and swap the final asset in later without a
layout rework. **Ride as an open question through initial E07 layout work**, but flag it for
`art-director`/`ux-designer` resolution before Vertical Slice content lock, as the document
itself already requests — this is the one item in this whole review where "riding" it
much longer starts to cost real rework risk (localization treatment differs completely
depending on whether the answer is "static art logo" vs. "localized text string," per §13).

### 3. World Map quick-mute control (`main-menu.md` §15)

**Not blocking — already effectively resolved by the document's own recommendation.** The
document recommends *against* adding a redundant quick-mute chip on World Map, correctly
reasoning that a second control surface for the same two booleans (`music_enabled`/
`sfx_enabled`) risks state divergence from the Settings screen's own controls, violating
`interaction-patterns.md`'s NEVER Pattern 9 (no UI element that silently diverges from actual
game state) unless it reads live with zero lag — a real risk with no design payoff proportional
to it. A `ui-programmer` implementing World Map today should simply **not build this control**;
that is the spec-consistent default. **Ride as an open question, default = do not build it**,
pending explicit `producer` confirmation only if this is ever prioritized.

### 4. Restart Level confirmation dialog (`pause-menu.md` §16)

**Not blocking — already effectively resolved by the document's own recommendation and its own
supplied reasoning.** The document recommends no confirmation dialog for Restart, using the

`interaction-patterns.md`'s pattern catalog hasn't formally added Restart as a second named
exception yet** — recommended as a small housekeeping edit at that document's next revision
pass (see `pause-menu.md`'s own verdict above), not a blocker for E07 implementation.

### 5. (Escalated by this review, not one of the original four) — `characters-and-tone.md`'s Draft status vs. its treatment as binding by APPROVED sibling GDDs
